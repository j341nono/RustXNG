## 指摘

優先度: P1は次のリリース前に対応すべき問題、P2は計画して対応すべき問題。

### A01 / P1: SSRF判定が接続先を保証しない

場所: `src/web/image_proxy.rs:82`、`src/network.rs:121`、`src/aggregator.rs:868`。

`is_public_url` はホスト名なら解決せず許可する。IPv6ではループバックと未指定しか
拒否せず、ULA・リンクローカル・IPv4 mappedな127.0.0.1も通る。
HTTPクライアントのリダイレクト制限は回数だけで、各遷移先を検証していない。
本文取得、画像・faviconプロキシに共通する。

ローカル再現: `localhost.`、`[::ffff:127.0.0.1]`、`[fc00::1]`、`[fe80::1]`
が判定を通った。`localhost.` からローカルサーバーへ接続し、リダイレクト後の本文を取得できた。
一般のホスト名が内部IPへ解決される場合も、接続時に止める処理はない。
公開ホストから内部ホストへの遷移はコード確認であり、このプローブでは実施していない。

対応: 信頼されたエンジンの接続と、検索結果URL等の非信頼接続を分ける。
後者では全解決IPを分類し、検証したIPへ接続を固定する。全リダイレクトを再検証し、
IPv4 mapped・非公開IPv6も拒否する。単なる事前DNS検査では再解決の競合が残る。

### A02 / P1: javascript URLが検索結果のリンクに残る

場所: `src/engine/util.rs:81`、`src/results.rs:1035`、`templates/results.html:65`付近。

共通URLヘルパーは小文字の `javascript:` しか拒否せず、JSONエンジン等からの
URLは中央の結果処理でもスキームを制限しない。HTMLエスケープはURLスキームを無害化しない。

ローカル再現: 偽Mwmblエンジンから返した `javascript:alert(1)` が、
`/search` のHTMLに `href="javascript:alert(1)"` として残った。
クリック時のスクリプト実行につながる。ブラウザーでの実行自体は試していない。
混在大文字の `JaVaScRiPt:` が共通ヘルパーを通ることも確認。

対応: エンジン単位に任せず、結果を表示する境界でURLを構文解析し、
用途別に許可スキームを制限する。画像・infoboxリンクにも同じ基準を適用する。
DBの `keyvalue:` はリンクとして表示しない既存動作を維持する。

### A03 / P1: 応答サイズ制限より前に全本文を読み込む

場所: `src/network.rs:366`、`src/web/image_proxy.rs:163`、`src/web/favicons.rs`、
`src/bin/rustxng-index.rs:533`。

通信層は `response.bytes()` で全本文を確保する。画像の8MiBやfaviconの512KiB判定は
その後なのでメモリ保護にならない。本文抽出・エンジン応答も同じで、並列取得時に増幅する。
クローラーも全本文を `text()` で読む。コード確認。OOMを起こす試験はしていない。

対応: 展開後バイト数をストリーム読取中に制限する。Content-Lengthだけに依存せず、
圧縮応答・chunked応答も上限で打ち切る。取得並列数にも上限を設ける。

### A04 / P1: /researchがレート制限を迂回する

場所: `src/web/handlers.rs:894`、`src/deep_research.rs:192`。

`/search` の `limiter.check` を `/research` は呼ばず、内部から検索を繰り返す。
LLM設定時は検索だけでなく外部LLM APIの呼出しも発生する。

ローカル再現: limiter_max=1で `/search` が429になる一方、
`/research` はその前後で200を返す。試験ではエンジンとLLMを無効にし、外部課金は発生させていない。

`/autocompleter` も同じlimiterを呼ばず、backendのカンマ区切りリストを入力の長さ分だけ順に試すため、
こちらも回数と全体期限の制限が必要（コード確認）。

対応: 研究APIにも共通の利用制限を適用し、同時実行数・全体期限・LLM利用の予算を設ける。

### A05 / P1: Cookie・ヘッダーが異なる検索でHTTPキャッシュを共有する

場所: `src/network.rs:224`、`src/cache.rs:82`。

キーはメソッド・URL・bodyだけ。SafeSearch CookieやAccept-Languageを区別しない。
formの区切り文字も構造として符号化されていない。

ローカル再現: 同一URLで `safe=strict` の後に `safe=off` を取得すると、
後者にも前者の応答が返った。PR #12のキャッシュキー修正が対象。

### A06 / P1: キャッシュ待ちが検索期限の外にある

場所: `src/network.rs:240`、`src/network.rs:251`、`src/cache.rs:301`。

期限設定前にキャッシュを読み、書込もtimeoutで囲まない。
Valkeyの応答停止やロック待ちにより検索が期限を超える。
失敗した接続を保持するため、プロトコルのずれも以後の操作へ持ち越せる。
コード確認。PR #12にローカルValkeyを使う回帰テストと修正がある。

対応: PR #12の期限・キャンセル時接続破棄の変更を取り込む。

### A07 / P2: リクエストのtimeout_limit=infでpanicする

場所: `src/web/handlers.rs:167`、`src/aggregator.rs:293`。

外部入力のf64を有限性・上限の検査なしで `Duration::from_secs_f64` に渡す。
`/search?q=rust&format=json&timeout_limit=inf` でリクエスト処理タスクのpanicを再現。
この環境ではプロセス全体の終了は確認していない。

対応: HTTP入口で有限・正数・サーバー上限内を検証し、不正値は400にする。
設定値と公開ライブラリAPIにも同様の検証を設ける。

### A08 / P2: 宣言している最低Rustバージョンでビルドできない

場所: `Cargo.toml:5`、`Cargo.lock`、`.github/workflows/ci.yml`。

rust-versionとREADMEは1.85以降を案内するが、tantivy 0.27は1.88、
time 0.3.55は1.88、datasketches 0.5は1.86を要求する。
`cargo +1.85.0 check --locked` の失敗を確認。

対応: 最低バージョンを実際に通る値へ変更するか、依存を互換版へ固定する。
CIに最低バージョンの検証を追加する。

### A09 / P2: 依存監査が失敗し、CIには監査ジョブがない

場所: `Cargo.lock`、`.github/workflows/ci.yml`、`docs/AI-INFRA.md`。

2026-10-30更新のRustSec DBによるcargo audit結果:

- `ctutils 0.4.2`: RUSTSEC-2026-0385（定数時間処理の問題）、修正版は0.4.4以降。
- `lru 0.12.5`: RUSTSEC-2026-0253、RUSTSEC-2026-0002のunsound警告。
- `basic-toml`、`fxhash`、`unsafe-libyaml`に保守終了警告。

ctutilsはpostgres-protocol、lruはmysql経由の既定DB機能の依存。
このアプリでの悪用可能性は未検証で、直ちにリモートコード実行が可能という指摘ではない。
AI-INFRA文書の「cargo auditをCIで実行」「既定ビルドの脆弱性0件」は現状と一致しない。

対応: 依存更新の可否と利用経路を確認し、解消・暫定抑制・残存理由を記録する。
監査をCIで実施し、README等の安全性表現も結果に合わせる。

### A10 / P2: サイト指定の再検索で元のQuery設定を失う

場所: `src/aggregator.rs:684`。

サイト指定の再検索でQueryを新しくparseするため、元の言語・SafeSearch・期間・
Query内のエンジン指定が失われる。SearchRequestのcloneだけでは保存されない。
コード確認。PR #12が元のQueryを維持する修正と回帰テストを持つ。

### A11 / P2: クロールの完了判定がリンク追加より先になる

場所: `src/bin/rustxng-index.rs:448`、`src/bin/rustxng-index.rs:465`。

in_flightを減らした後にページをwriterへ渡し、writer側がリンクをキューに入れる。
その間に全workerが終了できる。既存URLはwriterがcontinueするので子リンクも追加されない。
コード確認と、PR #13のローカルHTTP回帰テストで修正後の成功を確認。

### A12 / P2: Valkeyキャッシュのclearが実際のキーを削除しない

場所: `src/cache.rs:82`、`src/cache.rs:386`。

保存キーは `GET URL BODY` だがclearは `searxng:*` だけを検索する。
PR #12でキーがSHA-256になってもprefix不一致は残る。コード確認。

対応: 保存・読込・削除で同一namespaceを使い、大規模なKEYSはSCANに置き換える。

### A13 / P2: 不正な個別プロキシ設定で直接接続へ戻る

場所: `src/network.rs:170`。

個別proxyをparseできない場合やclient構築失敗時、エラーではなく既定clientへ戻る。
既定proxy未設定なら直接接続となり、指定した経路を通る保証がない。コード確認。
また全体proxyはschemeごとのキーを読みながら全てProxy::allにしており、
個別proxyより先に登録するため、全体proxy併用時の優先順位も要検証。

対応: 個別proxyの不正値は起動時エラーまたは当該エンジンの失敗にし、暗黙の経路変更を避ける。

### A14 / P2: LLMのJSON配列をカンマ分割している

場所: `src/deep_research.rs:150`。

`["Paris, Texas population", "a\\\"b"]` のような正規のJSONで、クエリ内の
カンマとエスケープを誤処理する。コード確認。
対応: `serde_json::from_str::<Vec<String>>` を使い、fenceの除去は別に行う。

### A15 / P2: ベンチマークが別ページを参照ページとして数え得る

場所: `tools/eval_quality.py:70`、`tools/eval_quality.py:142`。

単純なstartswith比較なので、goldが `/docs` の場合に `/docs-malicious` も一致する。
この例でhit_rank=1になることを再現した。意図的にディレクトリ配下を許可する場合でも、
パスセグメント境界を使う必要がある。
また `--restart-binary` はローカルbaseを作るが、検索にはargs.baseを使うため、
port/baseを明示的に揃えない呼出しでは再起動先と測定先がずれる。

対応: URLを構文解析し、一致条件を明文化する。実際の参照ページ到達率とQA正解率を分ける。
再起動先と検索先のbaseを統一し、既存の比較スコアは条件を固定して再測定する。

### A17 / P2: 部分設定ファイルが未指定の既定値まで上書きする

場所: `src/settings.rs:750`、`src/settings.rs:927`。

userファイルを先にSettingsへdeserializeするため、未指定フィールドにもRust側のDefaultが入る。
その後にserializeしてdeep_mergeするので、「未指定」と「明示した既定値」を区別できない。
`[server] port=18888` だけのファイルを渡すと、無関係なcache.max_bytesが同梱設定の32MiBから
Rust構造体の既定値8MiBへ変わることを再現した。ui.default_localeやsearch.default_langにも差がある。

対応: TOML/YAMLを値ツリーのまま同梱設定へマージしてからSettingsへdeserializeするか、
明示されたフィールドだけを保持するpartial-settings型を使う。

### A18 / P2: リリースノートのCHANGELOG抽出が常に空になる

場所: `.github/workflows/release.yml:156`。

awkの `want="## [$version]"` を正規表現として比較しているため、角括弧が文字クラスになる。
実際の `## [0.26.0]` 見出しとは一致せず、v0.26.0で抽出結果が0バイトになることを再現した。
その結果、CHANGELOGが存在しても汎用のフォールバック文でリリースを作成する。

対応: `index($0, want) == 1` 等の文字列比較を使い、見出し直後の境界も検証する。
既存バージョンの節が空でないことを公開前に検査する。

### A16 / P2: 大きいページ番号で55設定エントリが整数overflowする

場所: `src/engines/bing.rs:57`ほか、`src/web/handlers.rs:176`。

ページ上限は既定0（無制限）。284設定エントリ全件の初期化を試し、
成功した262件でページ1・2・u32::MAXのリクエスト生成と6種の空・不正応答解析を実施した。
全2,352ケース中、u32::MAXのリクエスト生成で55エントリがpanicした。
通常ページ1・2および小さな不正応答ではpanicなし。
初期化できなかった22件はAPIキーや接続設定不足等であり、その内部実装はこの動的検査の対象外。

デバッグビルドで再現済み。releaseでは同じ演算がwrapして誤ったoffsetになり得るが、
この検査ではreleaseの返却URLまでは確認していない。
対応: HTTP入口でページ番号を制限し、各エンジンもchecked arithmeticまたは広い整数型を使う。
[全ケース結果](audit/2026-11-02/engine-matrix.jsonl)と
[検査コード](audit/2026-11-02/engine-matrix.rs)を添付する。

文書にも追加の不一致がある。英語READMEの「search terms never leave it」は、
実装が各外部検索エンジンへ検索語を送る動作と一致しない。検索先と送信範囲を正確に記載すべき。

追加確認候補: DBのspawn_blockingはタイムアウトしてもDB処理を停止できず、MySQL等の実処理期限が不足する。
Valkey検索エンジンはSCANのcursorを一度しか処理せず、全キーを検索できない。
これらは実DB・実行環境を使った追加検証が必要。

## 再現プローブ

[probes.rs](audit/2026-11-02/probes.rs)は不具合の現状をassertする調査用コードで、
通常のテストスイートには組み込んでいない。mainで再実行する場合:

```bash
cp docs/audit/2026-11-02/probes.rs tests/audit_probes.rs
cargo test --test audit_probes -- --nocapture
rm tests/audit_probes.rs
```

修正後には該当プローブが失敗するため、製品テストへ移す際は「安全な挙動」のassertへ反転する。
全通信プローブはローカルのテストサーバーだけを使用する。
